# Final architecture review

This review reflects the current repository: a single Next.js App Router application, PostgreSQL/Prisma/pgvector, deterministic assessment/ranking/evaluation modules, and optional Ollama integrations. Findings marked **verified** are directly visible in the code/configuration. **Potential risk** means the repository does not include evidence to determine impact under a real deployment.

## Strengths

- **Verified:** Route handlers validate input with Zod and map known errors to structured responses.
- **Verified:** Retrieval, assessment, ranking, evaluation, and explanation responsibilities have separate module boundaries and tests.
- **Verified:** Matching traces link retrieval strategy/ranks, eligibility, signal contributions, and persisted result rows.
- **Verified:** Candidate responsibilities remain individual array entries, and responsibility evidence has stable item-level references.
- **Verified:** Eligibility distinguishes PASS/FAIL/UNKNOWN; rank and eligibility are not generated by the LLM.
- **Verified:** Explanation context is built from persisted decision evidence and falls back deterministically.
- **Verified:** Evaluation keeps manually authored relevance judgments apart from the ranker and records experiment configuration/results.
- **Verified:** PostgreSQL, FTS, and vector operations share one local database; no unneeded distributed service is present.

## Weaknesses and technical debt

- **Verified:** Core retrieval/ranking thresholds and default weights are heuristics/author decisions, not calibrated with independent real data.
- **Verified:** `Embedding.vector` is managed only in SQL and raw SQL, outside Prisma's typed schema. The schema column is fixed to 768 dimensions.
- **Verified:** Match/evaluation traces contain JSON snapshots; evolving their contracts needs explicit versioning/compatibility care.
- **Verified:** The dataset contains one experience record per candidate despite schema support for multiple; real-world completeness is not demonstrated.
- **Verified:** Candidate/job input is seeded data; there is no ingestion, auth, consent or retention workflow.
- **Verified:** Explanation support uses lexical overlap, which is a conservative heuristic, not semantic verification.

## Reliability and performance

- **Verified:** Matching has an explicit lexical fallback for typed semantic provider unavailability; general DB timeouts/retries and idempotency are not centrally configured.
- **Verified:** Exact vector scans are used and there is no approximate vector index; this is appropriate for 20 profiles, not proven for larger collections.
- **Verified:** Simultaneous first-time embedding work can duplicate compute before database upsert resolves the unique key.
- **Potential risk:** Concurrent API traffic may stress Prisma connection capacity or local Ollama; no load test quantifies the boundary.
- **Potential risk:** A model/dimension change can require a controlled re-embedding and migration process; no production rollout procedure is tested.

## Security, privacy, and trust

- **Verified:** Local Ollama integration and health API do not return secrets; logs avoid raw candidate/job text and stack traces.
- **Verified:** The application does not implement authentication/authorization, rate limits, real candidate consent, data deletion, or retention policy.
- **Potential risk:** Serving any imported real CV/job text would require an explicit privacy, access-control, retention, and threat-model review. Current synthetic inputs do not justify treating those controls as implemented.
- **Potential risk:** Prompt-injection separation is useful but not a model sandbox; LLM output must remain advisory and reviewed.

## Prioritized recommendations

| Priority | Recommendation | Finding type |
| --- | --- | --- |
| **Critical before any real candidate data or external demo deployment** | Add authentication/authorization, privacy/consent/retention/deletion controls, production secret handling, and a documented threat model. Keep the demo synthetic until then. | Verified absence; impact depends on deployment/data |
| **High** | Add independent, multi-reviewer relevance and eligibility evaluation data; audit subjective labels and ranking weights. | Verified evaluation limitation |
| **High** | Add request deadlines, DB/provider observability and load tests; define connection budgets and recovery behavior. | Verified lack of controls; scale risk unmeasured |
| **Medium** | Profile retrieval on a larger corpus and evaluate chunking, FTS behavior, model choices, and vector index before changing storage strategy. | Future scale evidence |
| **Medium** | Version persisted JSON trace schemas and define an embedding migration/re-embedding runbook. | Maintainability/deployment improvement |
| **Low** | Coalesce concurrent embedding generation and consider caching only if measured duplicate work is material. | Verified possible duplicate work, impact unmeasured |

No business logic was changed to improve the documentation. Recommendations above are proposals; none should be interpreted as a shipped capability.
